# CX CLI Hunt Integration — Design Spec

**Date:** 2026-05-13  
**Status:** Approved  
**Author:** Aviral Baloni

---

## Overview

Add a **"Hunt"** button to each detection suggestion generated by the Detection Builder. Clicking it navigates to a dedicated Hunt page that runs a two-step background investigation using the Coralogix native CLI (`cx`):

1. **Log Query** — executes `cx logs` with the detection's Lucene query to confirm real signal
2. **Olly AI Analysis** — sends the query and log results to Olly (Coralogix native AI) using a structured prompt, returning a 12-section hunting report
3. **Hunt Report** — a deliverable card that animates in at the end, synthesising findings, immediate actions, and an alert definition skeleton

Results are streamed progressively to the frontend via Server-Sent Events (SSE) so each step fills in as it completes.

---

## User Flow

```
Detection Builder
  └─ Generated detection card
       └─ [Hunt] button
            └─ Navigate to Hunt page (/hunt view)
                 ├─ Step 1: cx logs runs → query results fill in
                 ├─ Step 2: Olly analysis runs → 12 sections fill in (collapsed accordions)
                 └─ Step 3: Hunt Report card animates in (verdict + findings + actions + alert def)
                      ├─ [Open in Coralogix] deep link
                      └─ [Export Report] markdown download
```

## Frontend

### Hunt Button

- Added to each `FlowAlert` card in the Detection Builder generated panel
- Passes the full detection payload (name, logic, techniqueId, tacticId, window, source, severity) as URL/state to the Hunt view
- Single button per card — no confirmation dialog required

### Hunt Page (new view)

**Route:** SPA state transition, no full reload. Added to the existing `view` state machine alongside `'builder'`, `'alerts'`, etc.

**Page structure (top to bottom):**

```
← Back to Detection Builder
[Page title: Hunt: <detection name>]
[Meta badges: severity · techniqueId · tactic · source · window]

[3-step progress stepper: Log Query → Olly Analysis → Hunt Report]

[Section 1: Log Query]          ← fills on query_done SSE event
[Section 2: Olly Analysis]      ← fills on olly_done SSE event (12 collapsed accordions)
[Section 3: Hunt Report]        ← animates in on report_ready SSE event
```

### Skeleton States

Each section shows shimmer skeleton placeholders while its step is in progress:

| Step | Skeleton content |
|------|-----------------|
| Log Query | 3-column stat boxes + table row placeholders |
| Olly Analysis | Summary grid (3 cells) + objective block + badges + 4 accordion rows |
| Hunt Report | Full card shimmer matching the verdict/findings/actions layout |

Active step has a blue pulsing dot in the stepper; completed steps show a green check.

### Section 1 — Log Query Results (on `query_done`)

- `cx logs` command displayed in a monospace code block
- Stat boxes: total hits · hosts affected · last seen · unique users
- Log table: timestamp · host · user · command (truncated) · "Show N more events" expander

### Section 2 — Olly Analysis (on `olly_done`)

12 sections from the structured Olly prompt, rendered as collapsed accordions:

| § | Label | Default state |
|---|-------|--------------|
| 1 | Hunt Summary (severity, confidence, window, objective, MITRE) | Expanded |
| 2 | Original Query | Collapsed |
| 3 | Schema Mapping (table: original field → CX path → app/subsystem → gaps) | Collapsed |
| 4 | Translated Query — DataPrime | Collapsed |
| 5 | Translated Query — Lucene | Collapsed |
| 6 | Detection Logic Explained | Collapsed |
| 7 | Hunt Workflow | Collapsed |
| 8 | Suggested Aggregation / Pivot Query | Collapsed |
| 9 | False Positive Considerations | Collapsed |
| 10 | Visibility Gaps & Assumptions | Collapsed |
| 11 | Recommended Follow-up Hunts | Collapsed |
| 12 | Alert Definition Skeleton | Collapsed |

Visibility gaps (§10) are highlighted with a red alert card inside the accordion. Schema field gaps flagged in §3 appear in red within the mapping table.

### Section 3 — Hunt Report Deliverable (on `report_ready`)

Animates in at the bottom (`fadein` 400ms ease). Styled as a distinct deliverable card, not a section card.

**Header band** (coloured by verdict: green / amber / red):
- Verdict label: `HUNT REPORT · <Threat Detected | Suspicious Activity | No Threats Found> · <Confidence>`
- Title: one-line plain-language verdict
- Subtitle: 1-2 sentence summary with key entities
- Stat row: hits · hosts · attack window · C2 flag (contextual)

**Body:**
- **Key Findings** — 3-5 bullet points extracted from §1 + §6 + §10
- **Immediate Actions** — numbered list from §11 recommendations, priority-ordered (critical / warning / info)
- **Alert Definition Skeleton** — compact key-value grid from §12 (name, type, condition, severity, group-by)

**Footer:**
- Run timestamp + duration
- `[Open in Coralogix]` — deep link to Explore with the translated Lucene query
- `[Export Report]` — triggers markdown download via `/api/hunt/:id/export`

### Verdict Derivation

Derived from §1 (`Severity` + `Confidence`) combined with the cx logs hit count:

| Condition | Verdict |
|-----------|---------|
| hits = 0 | No threats found (green) |
| hits > 0, Confidence = Low or Severity ≤ Medium | Suspicious activity (amber) |
| hits > 0, Confidence = High or Severity ≥ High | Threat detected (red) |

## Backend

### New Endpoint: `GET /api/hunt/stream`

**Query params:**
```
detection_id  string   required  — references a stored detection payload
```

Detection payloads are stored in **Redis** (already in the stack) when the Detection Builder generates them. Key: `hunt:<detection_id>`, TTL: 1 hour.

When the SSE connection opens, the server generates a `hunt_id` (UUID) and stores the in-progress/completed result under `hunt_result:<hunt_id>` in Redis (TTL: 1 hour). The frontend receives this ID in the first event and uses it for the export endpoint.

**Response:** `Content-Type: text/event-stream` with SSE events:

```
event: stream_opened
data: {"hunt_id": "uuid-v4"}

event: query_done
data: {"hits": 47, "hosts": 3, "last_seen": "2m", "unique_users": 2,
       "sample_events": [...], "cx_command": "cx logs '...' --start now-5m"}

event: olly_done
data: {"sections": {"1": {...}, "2": {...}, ..., "12": {...}}}

event: report_ready
data: {"verdict": "threat", "confidence": "high", "title": "...",
       "subtitle": "...", "stats": {...},
       "findings": [...], "actions": [...], "alert_def": {...}}

event: error
data: {"code": "cx_timeout", "message": "..."}
```

### cx Execution (Go)

```go
// Allowlisted commands only — never sh -c
allowlist := []string{"logs", "olly"}

func runCxLogs(ctx context.Context, query string, window string) ([]byte, error) {
    // args as slice — no shell interpolation
    cmd := exec.CommandContext(ctx, cxBinPath, "logs", query,
        "--start", "now-"+window, "--output", "agents", "--limit", "50")
    // output capped at 64KB
    return readCapped(cmd, 64*1024)
}

func runCxOlly(ctx context.Context, prompt string) ([]byte, error) {
    cmd := exec.CommandContext(ctx, cxBinPath, "olly", "chat", prompt)
    return readCapped(cmd, 64*1024)
}
```

**Context:** 45-second deadline. Client disconnect cancels the context, which sends SIGKILL to the cx subprocess.

### Input Sanitisation

The Lucene query from the detection payload (LLM-generated) is sanitised before exec:

1. Passed as a single argument to `exec.Command` — no shell expansion possible
2. Validated against a regex allowlist: only printable ASCII, no `$()`, backticks, semicolons, pipes, or newlines
3. Length capped at 1000 characters
4. If validation fails: return `error` SSE event, do not exec

### Olly Prompt Template

The standard prompt (as defined by the product owner) is stored as a Go template constant. The detection's Lucene query and cx logs output are interpolated at runtime:

```
{{.SystemPrompt}}

## QUERY TO HUNT
{{.LuceneQuery}}

## LOG RESULTS (cx logs output)
Total hits: {{.HitCount}}
Sample events:
{{.SampleEvents}}
```

### cx Binary Configuration

```
CX_BIN_PATH   path to cx binary (required)
CX_API_KEY    Coralogix API key for cx authentication (required)
CX_REGION     Coralogix region slug, e.g. "eu2" (required, used for deep links)
CX_PROFILE    cx profile name (optional, defaults to default profile)
```

cx is authenticated via `cx profiles` configured at server startup, not per-request.

### Export Endpoint: `GET /api/hunt/:id/export`

Serialises the `report_ready` payload to a markdown document and serves it as:
```
Content-Disposition: attachment; filename="hunt-<detection-name>-<date>.md"
Content-Type: text/markdown
```

### "Open in Coralogix" Deep Link

Constructed from the §5 translated Lucene query + `CX_REGION`:
```
https://<CX_REGION>.coralogix.com/#/query-new/logs?query=<url-encoded-lucene>
```

```typescript
// New types to add to frontend/src/types/index.ts

interface HuntPayload {
```

## Security Constraints

| Constraint | Implementation |
|------------|---------------|
| No arbitrary shell exec | `exec.Command` with args as slice only; no `sh -c` |
| No command injection | Query validated against allowlist regex before exec |
| Allowlisted subcommands | Only `cx logs` and `cx olly chat` permitted |
| Process isolation | Each hunt spawns a fresh process with a context deadline |
| Output cap | 64 KB max from cx stdout; truncated beyond that |
| Timeout | 45s hard deadline; process killed on expiry |
| Client disconnect | Context cancel propagates SIGKILL to subprocess |
| Binary path | Hardcoded from `CX_BIN_PATH` env var — not resolved from PATH |
| Rate limiting | Max 3 concurrent hunts per server instance (configurable via `HUNT_MAX_CONCURRENT`) |

---

## Out of Scope

- Persisting hunt results to the database (in-memory only, TTL 1h)
- Creating alert rules directly from the hunt page (user reads the alert definition skeleton and creates manually)
- Multi-tenant hunt isolation (single-tenant deployment assumed)
- Hunt history / re-running past hunts
- Streaming Olly output token-by-token (full response awaited before `olly_done` event)
