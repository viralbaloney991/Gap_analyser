### Task 5: Tooltip viewport boundary clamping (MITREHeatmap)

**Files:**
- Modify: `frontend/src/components/MITREHeatmap.tsx`

**Background:**  
The tooltip is positioned at `style={{ left: tooltip.x, top: tooltip.y }}` — exact mouse coordinates with no boundary checking. Near the right or bottom edge, the tooltip overflows off-screen. Fix: clamp `x` and `y` using `window.innerWidth` / `window.innerHeight` when setting tooltip state.

The tooltip state is set via `setTooltip` calls where mouse events fire. Search for `setTooltip({` to find all call sites.

- [ ] **Step 1: Read the tooltip state shape**

Read `frontend/src/components/MITREHeatmap.tsx` and find the `tooltip` state type and `setTooltip` calls (search for `setTooltip`).

The tooltip CSS has `white-space: nowrap` so approximate width is `text.length * 7 + 20` px. Height is ~28px.

- [ ] **Step 2: Add a clamp helper**

`MITREHeatmap.tsx` has TWO separate components, each with its own tooltip state (at lines ~173 and ~714). The existing code already adds `+ 12` / `- 8` offsets inline. The fix clamps those already-offset values.

In the first component (the force-graph component — `tooltip` state at line 173), add this helper immediately after the tooltip state declaration:

```typescript
const clampTooltip = (x: number, y: number, text: string) => ({
  x: Math.min(x, window.innerWidth  - Math.min(text.length * 7 + 24, 320)),
  y: Math.min(y, window.innerHeight - 36),
  text,
});
```

In the second component (the heatmap component — `tooltip` state at line ~714), add the **identical** helper immediately after that tooltip state declaration.

- [ ] **Step 3: Update the three `setTooltip` calls that set coordinates**

There are exactly three `onMouseEnter` handlers that set tooltip coordinates. Replace each one:

**Line ~321** (force-graph technique nodes):
```typescript
// BEFORE:
onMouseEnter={(e) => setTooltip({ x: e.clientX + 12, y: e.clientY - 8, text: `${t.techniqueID} · ${t.name ?? t.techniqueID}` })}
// AFTER:
onMouseEnter={(e) => setTooltip(clampTooltip(e.clientX + 12, e.clientY - 8, `${t.techniqueID} · ${t.name ?? t.techniqueID}`))}
```

**Line ~382** (force-graph tactic nodes):
```typescript

```

**Lines ~884–888** (heatmap technique cells):

### Task 6: ClientSelector explicit loading state

**Files:**
- Modify: `frontend/src/components/ClientSelector.tsx`

**Background:**  
The current loading detection uses `clients.length === 0 && !fetchError`. This works but races: if `fetchClients()` resolves immediately with an empty array, the UI incorrectly shows skeletons forever. Adding an explicit `isLoading` boolean makes intent clear and eliminates the ambiguity.

- [ ] **Step 1: Add `isLoading` state to ClientSelector**

In `frontend/src/components/ClientSelector.tsx`, find the existing state declarations (~line 23):

```typescript
  const [clients, setClients]         = useState<ClientInfo[]>([]);
  const [selected, setSelected]       = useState('');
  const [fetchError, setFetchError]   = useState('');
  const [searchQuery, setSearchQuery] = useState('');
```

Add `isLoading`:

```typescript
  const [clients, setClients]         = useState<ClientInfo[]>([]);
  const [selected, setSelected]       = useState('');
  const [fetchError, setFetchError]   = useState('');
  const [searchQuery, setSearchQuery] = useState('');
  const [isLoading, setIsLoading]     = useState(true);
```

- [ ] **Step 2: Update the useEffect to set isLoading**

Find (~line 28):
```typescript
  useEffect(() => {
    fetchClients()
      .then(setClients)
      .catch(() => setFetchError('Failed to load client list'));
  }, []);
```

Replace with:
```typescript
  useEffect(() => {
    setIsLoading(true);
    fetchClients()
      .then(setClients)
      .catch(() => setFetchError('Failed to load client list'))
      .finally(() => setIsLoading(false));
  }, []);
```
